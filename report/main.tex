\section{Overview, Assumptions and Key Decisions}
Partners upload a 1--5\,GB image batch; each job runs \emph{prep} (CPU) $\rightarrow$
\emph{species ID} (GPU) $\rightarrow$ \emph{report} (CPU). Four principles drive the design.
(i)~One transactional store (PostgreSQL) holds job state, the queue and leases, so there is never a
dual-write between a queue and a database.
(ii)~\emph{Execution is at-least-once, publication is exactly-once}: workers pull fenced leases, write
create-only per-attempt objects, and a conditional database update publishes exactly one attempt.
(iii)~\emph{Compute is active-active across AWS and GCP; the database writer is active-passive}, and jobs
run data-locally to avoid egress.
(iv)~\emph{Recovery never promotes a stale database}: the standby takes over writes only after the old
writer is fenced and the standby is verified complete. When safety and write availability conflict,
safety wins.

\section{One Job's Lifecycle}
\begin{sloppypar}
\textbf{States.} Job: \texttt{UPLOADING} $\rightarrow$ \texttt{ACCEPTED} $\rightarrow$ \texttt{RUNNING}
$\rightarrow$ \texttt{FINALISING} $\rightarrow$ \texttt{COMPLETED}; side exits \texttt{FAILED\_NEEDS\_REVIEW},
\texttt{CANCELLED}. Each stage: \texttt{QUEUED} $\rightarrow$ \texttt{RUNNING} $\rightarrow$
\texttt{SUCCEEDED}, with \texttt{RETRY\_WAIT} and \texttt{FAILED}. Job and attempt IDs are UUIDs.
(1)~The partner signs in through its IdP. The job service validates the JWT (issuer, audience,
signature, expiry) and maps the partner to a tenant on the server side.
(2)~\texttt{POST /jobs} (file list, sizes, SHA-256) picks the home cloud (healthy, earliest estimated
finish) and returns per-object multipart-upload URLs scoped to \texttt{jobs/\{id\}/input/} in the tenant
bucket (15\,min, renewable after re-authentication for slow links).
(3)~The client uploads directly; failed parts are retried individually, and abandoned multipart uploads
expire by lifecycle rule.
(4)~\texttt{POST /jobs/\{id\}:submit} carries a tenant-scoped \texttt{Idempotency-Key} and a request hash.
The service verifies sizes and SHA-256 (multipart ETags are not content hashes). One primary transaction
then records \texttt{ACCEPTED}, the immutable input manifest, the pinned image and model versions and
\texttt{PREP\_QUEUED}, and \texttt{202} is returned only after that commit. Durability comes from the Multi-AZ
primary and versioned home storage, so acceptance needs no synchronous cross-cloud copy. If the primary
is unavailable, the API returns a retryable error, never a false acceptance. A retry returns the same
job; reusing a key with a different request is rejected.
(5)~A ready CPU runner in the home cloud claims the prep lease.
(6)~It writes \texttt{stage1/attempt-\{uuid\}/}. The coordinator publishes it (\S\ref{sec:fail}), marking the
stage \texttt{SUCCEEDED} and queuing stage 2 in the same transaction; stage 3 follows the same way.
(7)~A finaliser copies the report to both clouds and verifies the hashes while the job is
\texttt{FINALISING}. One transaction then records \texttt{COMPLETED}, both object versions and a notification
outbox event, and a reconciler mirrors a small \emph{completion-catalog} entry to GCP for outage reads.
Notifications are at-least-once with a stable event ID. \texttt{GET /jobs/\{id\}} shows stage, queue
position and ETA; reports download via 5-minute presigned URLs.
\end{sloppypar}

\section{Job Coordination and Placement}
\textbf{Acceptance and tracking.} The \texttt{jobs} and \texttt{stage\_runs} tables are the single source of
truth. Each stage row holds \texttt{status}, \texttt{epoch}, \texttt{attempt\_id}, \texttt{owner},
\texttt{lease\_expires\_at} (database clock only) and \texttt{published\_attempt}. Load is $<$1\,write/s, so
a separate broker (SQS/Pub/Sub) would add a dual-write hazard without benefit.

\textbf{Worker discovery and assignment (pull).} A small \emph{runner agent} is baked into each stage image.
It authenticates with workload identity and calls \texttt{POST /leases} with its capabilities
(\texttt{cloud}, \texttt{pool}, allocatable memory, GPU model and VRAM, readiness), which the coordinator
checks against the pool's configured identity. The coordinator selects an eligible row with
\texttt{SELECT \ldots FOR UPDATE SKIP LOCKED} and, in the same transaction, sets \texttt{RUNNING},
increments \texttt{epoch}, creates a new \texttt{attempt\_id}, records the owner and sets a 90\,s lease. The
runner renews the lease every 30\,s. Only a claim increments the epoch. No registry is needed: a worker
exists while it holds or requests leases. Pull also balances load naturally, because idle (and faster)
runners ask for the next item sooner.

\textbf{Stage dependencies.} A stage becomes \texttt{QUEUED} only in the transaction that marks its
predecessor \texttt{SUCCEEDED}. Consumers require \texttt{status=SUCCEEDED} and read only the published
manifest, never a prefix listing.

\textbf{Resources and fairness.} At acceptance, each job gets a resource profile from image count and decoded
image size (batch bytes alone do not predict peak memory) plus the model's VRAM. A lease matches only a
compatible pool, and GPU stages run only on tainted GPU pools. Ordering is \emph{weighted fair share across
tenants}, then oldest first. A per-tenant GPU concurrency cap (default 2) stops one partner's 50-job
burst from starving the others; unused share may be borrowed.

\textbf{Placement.} Work is placed by \emph{estimated finish time} (queue wait + measured stage runtime +
transfer). Prep runs in the home cloud. Stage 2 \emph{spills} only if
$\mathrm{ETA}_{remote} + t_{transfer} + 20\,\mathrm{min} < \mathrm{ETA}_{local}$ (hysteresis). It then copies and
verifies the \emph{published} prepared output ($\approx$150--300\,MB) rather than the raw 3\,GB batch,
roughly 10--20$\times$ less egress. The report stage stays next to the identification output.

\section{VMs, Containers and Orchestration}
\textbf{Provisioning (IaC).} Terraform modules per cloud (VPC, VPN/BGP, EKS/GKE, node pools, buckets with
lifecycle rules, KMS, primary and standby databases, IAM) plus a global stack (DNS). State is encrypted,
locked and access-restricted. GitHub Actions runs \texttt{plan} on pull requests and \texttt{apply} after
review, authenticating through OIDC federation, so CI holds no cloud keys. Kubernetes manifests are
\emph{plain YAML} (a shared base plus small per-cloud files), extending the \texttt{kubectl} workflow of my A1
SmartPark deployment. After tests, scanning and signing, CI substitutes image digests and runs
\texttt{kubectl apply} against both clusters, and a scheduled \texttt{kubectl diff} reports drift.
Helm + Argo CD would cut duplication and drift further but add controllers, permissions and upgrades;
for two clusters and three stage images the simpler toolchain wins. Schema migrations and the failover
runbook are rehearsed with each release.

\textbf{Holding the cap.} Node pools have \texttt{max\_size} system 1, CPU 7 and GPU 2 per cloud. The cap must
also hold during upgrades and repairs. Surge is therefore disabled (EKS \texttt{MINIMAL} node-group updates,
GKE zero-surge), so a node is removed before its replacement is created. Dedicated accounts and projects
with restricted provisioning roles stop anyone adding pools outside Terraform, and an alert fires at 19
VMs. An \emph{unreachable} VM still counts: capacity is never reclaimed until its termination is
confirmed. CPU workers use spot instances, because a preemption is just another lease expiry. GPU
workers and system nodes are on-demand.

\textbf{Containers.} Each stage has one image: the supplied program plus the runner agent and its
libraries. Images are built once in CI, scanned, signed (cosign), pushed to both registries and deployed
\emph{by digest}. The GPU image pins CUDA and framework versions and a tested host-driver range. As in A1,
model weights are \emph{not} baked into the image: an init container fetches \texttt{model@version} from our
bucket, verifies its SHA-256, and stores it in a node-local, read-only, model-only cache. Tenant data
never enters that cache.

\textbf{Isolation and scaling.} Unlike SmartPark's long-running inference pods, each stage attempt is a finite
Kubernetes Job. KEDA \emph{ScaledJobs} launch one single-use pod per eligible queued lease and count active
and pending pods to avoid over-launching. A pod requests a lease only after its startup checks pass, runs
exactly one attempt and exits; an empty pull exits at once. Every tenant job therefore gets a fresh pod
with its own scratch \texttt{emptyDir}. Requests cover CPU, RAM, ephemeral disk and GPU, and required pod
anti-affinity places one attempt per worker VM, leaving room for node agents. The cluster autoscaler
works within the pool bounds, and GPU pools scale to zero after 10\,min idle (one stays warm in business
hours). Pods run as non-root with a read-only root filesystem, all capabilities dropped and seccomp.
NetworkPolicy is default-deny: egress is allowed only to the coordinator, identity, DNS, model and storage
endpoints. This sharply reduces, but cannot eliminate, the risk of a third-party program exfiltrating
data.

Images and models referenced by retained reports are kept for the report's lifetime.

\section{Health and Recovery}
\textbf{Readiness.} A startup check verifies the model checksum, GPU allocation and a CUDA self-test, free
scratch space, and that storage and the coordinator are reachable; only then does the runner claim work.
Node health comes from the kubelet and GPU (Xid) errors.

\textbf{Crashes.} A non-zero exit or OOM is reported by the agent. A lost pod, VM, preemption or partition
appears as missing heartbeats. The reaper locks the row, confirms expiry on the database clock, marks the
attempt \texttt{ABANDONED} and requeues the stage; the next claim increments the epoch.

\textbf{Stalls.} Heartbeats prove only that the agent is alive, not that useful work is happening, so they
also carry progress: output bytes, program progress where available, and GPU utilisation for stage 2
(an idle CPU does not mean a GPU kernel has stalled). No progress for 10\,min, or exceeding 2$\times$ the
historical p99 for the size class and hardware, kills and requeues the attempt. The agent also stops
itself when it cannot renew, but safety never depends on that (\S\ref{sec:fail}).

\textbf{Repeated failures} are classified:
(a)~\emph{transient program failures} are retried at most twice with exponential backoff and jitter, and an
OOM moves to a larger-memory pool;
(b)~\emph{deterministic input or configuration errors} are not retried and go to the partner with a reason;
(c)~\emph{infrastructure failures} have a separate budget (5 attempts or 24\,h) and lower the node's health
score, and 2 failures from different jobs within 1\,h quarantine the node.
These budgets are initial defaults, tuned with fault-injection tests. An exhausted budget leaves the job
\texttt{FAILED\_NEEDS\_REVIEW}: its data is kept, an alert fires, and the queue continues. Cancellation
invalidates leases and blocks publication.

\textbf{Logs and metrics.} Structured logs carry \texttt{tenant, job, stage, attempt, epoch, trace ID, image
digest, model hash} and failure category, never image contents or secrets. Metrics and alerts: oldest
queue age, stage latency by size and hardware, GPU utilisation and VRAM, lease-expiry and retry rates,
tenant fairness, report-copy backlog, replication lag, VM count vs.\ cap, egress bytes and stalled
finalisation.

\section{Failure Scenario: GPU VM Lost After Writing Its Output}\label{sec:fail}
\begin{table}[H]\centering\small
\begin{tabularx}{\linewidth}{@{}p{1.25cm}Y@{}}
\toprule
\textbf{Time} & \textbf{Event and state change} \\ \midrule
$t_0$ & G1 has claimed stage 2 of job J: \texttt{epoch=7}, attempt \texttt{A}. It writes \texttt{stage2/attempt-A/}
  with create-only writes, then a manifest of object versions and SHA-256. Only the coordinator can move
  the publication pointer. \\
$t_1$ & G1 becomes unreachable before committing; its heartbeats stop. Its storage credentials may outlive the
  lease (AWS STS sessions last $\geq$15\,min) but can write only \texttt{attempt-A/}, which nobody reads unless it is
  published. Credentials are therefore \emph{not} the safety mechanism. \\
$t_1$+90\,s & The reaper locks the row, confirms expiry on the DB clock, marks \texttt{A} \texttt{ABANDONED} and sets the
  stage \texttt{QUEUED}; \texttt{epoch} stays 7. A commit from G1 now fails, because the stage is not \texttt{RUNNING}. \\
$t_2$ & G2 claims the stage (\texttt{epoch=8}, attempt \texttt{B}), writes \texttt{attempt-B/} and commits in one short
  transaction: lock the row, then
  \texttt{UPDATE stage\_runs SET status='SUCCEEDED', published\_attempt='B' WHERE job=J AND stage=2 AND attempt\_id='B'
  AND owner='G2' AND epoch=8 AND status='RUNNING' AND lease\_expires\_at > clock\_timestamp()} $\rightarrow$ 1 row,
  and queue stage 3 in the same transaction. (\texttt{clock\_timestamp()}, not \texttt{now()}, which is fixed at
  transaction start.) An identical repeated commit returns the recorded success. \\
$t_3$ & G1 returns and commits with \texttt{epoch=7}, attempt \texttt{A} $\rightarrow$ 0 rows $\rightarrow$ \texttt{409 STALE\_LEASE}.
  The agent discards its work and exits. Kubernetes has already deleted the pod, so the kubelet kills it on
  reconnect. \\
$t_3$+24\,h & GC confirms that \texttt{A} is unreferenced and deletes \texttt{attempt-A/}. \\
\bottomrule
\end{tabularx}
\end{table}
\vspace{-6pt}
\textbf{Why there is no duplicate or conflicting result.}
(a)~Attempts never share a path, and writes are create-only, so G1 cannot overwrite G2.
(b)~Exactly one attempt can satisfy the predicate, and cancellation takes the same row lock.
(c)~Consumers require \texttt{SUCCEEDED} plus the published pointer, so an orphan is invisible.
(d)~\texttt{COMPLETED} and the outbox event are written in one transaction, and notifications carry a stable ID.
(e)~Lease time is the database's clock, so drift on G1 cannot help it.
The guarantee is one \emph{authoritative published result}, not one physical execution. \emph{Considered and
rejected:} adopting G1's verified orphan would save $\approx$6 GPU-min and is safe with create-only objects,
but it adds a second publication path, so we rerun instead.

\section{Multi-Cloud Operation}\label{sec:mc}
\textbf{Strategy: active-active compute, active-passive database writer.} Both clouds run job services and
workers every day, so compute failover capacity is always warm and tested. The only singleton is the
PostgreSQL writer (AWS); GCP's job service writes to it over the VPN, and GCP holds an async replica for
outage reads and controlled promotion. A multi-master database would need $\geq$3 regions for quorum and a
further third-party dependency, which is too much for 100 jobs/day.

\textbf{Connectivity and egress.} AWS Site-to-Site VPN $\leftrightarrow$ GCP HA VPN (4 tunnels, BGP,
non-overlapping CIDRs), with TLS to the database and mTLS between services. Cross-cloud traffic is DB
replication, GCP-to-primary writes, report and catalog copies, and rare spills, sent by a copier service
to private storage endpoints where supported (otherwise approved HTTPS egress). Partners' presigned-URL
traffic never crosses clouds. Replicating every raw input would move $\approx$9\,TB/month
($\approx$\$1{,}080--1{,}710); data-local placement leaves reports (100$\times$10\,MB$\times$30 $\approx$
30\,GB/month, $\approx$\$4--6) plus DB replication, logs and occasional spills ($\approx$\$0.02--0.06 each).
A dedicated interconnect is not justified at this volume.

\textbf{Recovery policy.} \emph{Routing is automatic}: DNS health checks from several locations move partner
traffic to a healthy job service (target $\approx$3\,min plus client DNS caching), and runners claim only work
they can reach. \emph{Writer failover is a scripted, operator-approved runbook}, because asynchronous
replication alone cannot prove that nothing was lost:
(1)~pause admission, claims and publication;
(2)~fence the old writer through the AWS control plane (block all client paths to the primary and
terminate remaining sessions); an elapsed lease or a timeout is not proof;
(3)~read the primary's final committed WAL position and wait until the standby has applied it, including
pointers, cancellations and idempotency records;
(4)~promote once, switch the writer endpoint, bump the coordinator generation so old leases are invalid,
and resume. If (2) or (3) cannot be established, for example because the primary cannot be reached even
through its control plane, the system stays read-only and waits; it never promotes a stale history.

\begin{tabularx}{\linewidth}{@{}p{2.6cm}Y@{}}
\toprule
\textbf{Failure} & \textbf{What continues; what waits} \\ \midrule

  apply). Admission, claims and publication wait for AWS or a proven-safe promotion; running attempts may

\vspace{-6pt}
\textbf{Objectives} (targets, validated in drills): reads re-routed in $\approx$3\,min; writes resume
$\approx$5\,min after fencing and verification succeed, with no bounded write RTO during an ambiguous
partition. Acknowledged decisions are never lost by promotion, because only a verified-complete standby is
promoted; report bytes have two verified copies before \texttt{COMPLETED}. \textbf{Failback:} the old primary is
rebuilt as a replica and switched back in a quiet window; it never rejoins as an independent writer.

\section{Cloud Security}
\textbf{Users.} Partners sign in through OIDC with MFA; the JWT's issuer, audience, signature and expiry are
validated, and the tenant is mapped server-side. Automation uses scoped OAuth client credentials.
\textbf{Services.} Workloads use workload identity (EKS Pod Identity, GKE Workload Identity), so no
static cloud keys exist. Internal APIs use mTLS, and database connections use TLS.

\textbf{Access control (defence in depth).}
(1)~The tenant comes from the token, never from the request body, and ownership is checked on every call.
(2)~PostgreSQL row-level security: \texttt{SET LOCAL app.tenant\_id} in each transaction, application roles
that are not table owners and lack \texttt{BYPASSRLS}, and a separate restricted role for the coordinator.
(3)~One bucket and one KMS key per tenant per cloud; both report copies and the completion catalog get the
same tenant checks.
(4)~Runners get only the exact input and model reads and attempt-prefix writes they need, and cannot
publish DB state or delete reports. Because STS sessions last at least 15\,min, the coordinator's lease,
not the credential, is the authority.
(5)~Presigned URLs are per object and short-lived.
Retiring a tenant's key crypto-shreds its data once retention and backup obligations are reconciled.

\textbf{Secrets.} Secrets live in AWS Secrets Manager / GCP Secret Manager, are read at run time through
workload identity and are rotated; databases use IAM authentication. CI runs secret scanning.
\textbf{Network isolation.} Workers and databases are private (no public IPs) and use private storage
endpoints. The API sits behind a WAF and rate limits, and admission control (Kyverno / Binary
Authorization) admits only signed images.
\textbf{Encryption.} TLS 1.2+ externally, mTLS internally, and IPsec between clouds. At rest: SSE-KMS/CMEK
with per-tenant keys, and KMS-encrypted databases, disks and backups. Audit trail: CloudTrail data events,
GCS data-access logs, and DB audit of every state transition.

\section{Trade-offs and Limitations}
\textbf{Safety over write availability:} if fencing or completeness cannot be proven, the system stays
read-only rather than risk two writers or a stale history. A research workload of 100 jobs/day can
tolerate hours of delayed writes, but not wrong results. \textbf{Plain YAML + CI over Helm/Argo CD:} simpler
to run and explain, at the cost of some duplication. \textbf{Inputs are not replicated}: this saves
$\approx$\$1.1--1.7k/month but pauses home-cloud jobs during an outage. \textbf{Scale-to-zero GPUs} save
$\approx$\$2.7k/month for a $\approx$5\,min cold start. Retry budgets, recovery targets and prices are initial
values, to be validated with drills and the providers' calculators.
