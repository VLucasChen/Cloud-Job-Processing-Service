\section{Overview, Assumptions and Key Decisions}
Partners upload a 1--5\,GB image batch; each job runs \emph{prep} (CPU) $\rightarrow$
\emph{species ID} (GPU) $\rightarrow$ \emph{report} (CPU). Four principles drive the design.
(i)~One transactional store (PostgreSQL) holds job state, the queue and leases, so there is never a
dual-write between a queue and a database.
(ii)~\emph{Execution is at-least-once, publication is exactly-once}: workers pull fenced leases, write
create-only per-attempt objects, and a conditional database update publishes exactly one attempt.
(iii)~A result becomes \emph{visible} only after a small receipt for it exists in \emph{both} clouds, so
a lagging replica can be reconciled without producing a conflicting result.
(iv)~\emph{Compute is active-active across AWS and GCP, the database writer is active-passive}, and
jobs run data-locally to avoid egress. When safety and write availability conflict during an
ambiguous partition, safety wins.

\section{One Job's Lifecycle}
\begin{sloppypar}
\textbf{States.} Job: \texttt{UPLOADING} $\rightarrow$ \texttt{ACCEPTANCE\_PENDING} $\rightarrow$
\texttt{ACCEPTED} $\rightarrow$ \texttt{RUNNING} $\rightarrow$ \texttt{COMPLETED}; side exits
\texttt{FAILED\_NEEDS\_REVIEW}, \texttt{CANCELLED}. Each stage: \texttt{QUEUED} $\rightarrow$
\texttt{RUNNING} $\rightarrow$ \texttt{PUBLISHING} $\rightarrow$ \texttt{SUCCEEDED}, with \texttt{RETRY\_WAIT} and \texttt{FAILED}.
(1)~The partner signs in through its IdP. The job service validates the JWT (issuer, audience,
signature, expiry) and maps the partner to a tenant on the server side.
(2)~\texttt{POST /jobs} (file list, sizes, SHA-256) picks the home cloud (healthy, earliest estimated
finish) and returns per-object multipart-upload URLs scoped to \texttt{jobs/\{id\}/input/} in the tenant
bucket (15\,min, renewable after re-authentication for slow links).
(3)~The client uploads directly; failed parts are retried individually.
(4)~\texttt{POST /jobs/\{id\}:submit} carries a tenant-scoped \texttt{Idempotency-Key}. The service verifies
sizes and SHA-256 (multipart ETags are not content hashes) and commits \texttt{ACCEPTANCE\_PENDING} with an
outbox item. It then writes an immutable \emph{acceptance receipt} (input versions and hashes, home cloud,
pinned image and model versions) to both clouds, commits \texttt{ACCEPTED} + \texttt{PREP\_QUEUED}, and only
then returns \texttt{202}. A retry with the same key resumes the same job. Lack of capacity only means
queueing.
(5)~A ready CPU runner in the home cloud claims the prep lease.
(6)~It writes \texttt{stage1/attempt-\{uuid\}/} and the coordinator publishes it (\S\ref{sec:fail}), which
queues stage 2; stage 3 follows the same way.
(7)~The report is copied and checksum-verified in both clouds and a completion receipt is mirrored. One
transaction then records \texttt{COMPLETED}, both object versions and a notification outbox event. Notifications are
at-least-once with a stable event ID for de-duplication. \texttt{GET /jobs/\{id\}} shows stage, queue
position and ETA; reports download via 5-minute presigned URLs.
\end{sloppypar}

\section{Job Coordination and Placement}
\textbf{Acceptance and tracking.} The \texttt{jobs} and \texttt{stage\_runs} tables are the single source of
truth. Each stage row holds \texttt{status}, \texttt{epoch}, \texttt{attempt\_id}, \texttt{owner},
\texttt{lease\_expires\_at} (database clock only) and \texttt{published\_attempt}. Load is $<$1\,write/s, so
a separate broker (SQS/Pub/Sub) would add a dual-write hazard without benefit.

\textbf{Worker discovery and assignment (pull).} A small \emph{runner agent} is baked into each stage image.
It authenticates with workload identity and calls \texttt{POST /leases} with its capabilities
(\texttt{cloud}, \texttt{pool}, allocatable memory, GPU model and VRAM, readiness), which the coordinator
checks against the pool's configured identity. The coordinator selects an eligible row with
\texttt{SELECT \ldots FOR UPDATE SKIP LOCKED} and, in the same transaction, sets \texttt{RUNNING},
increments \texttt{epoch}, creates a new \texttt{attempt\_id}, records the owner and sets a 90\,s lease. The
runner renews the lease every 30\,s. No registry is needed: a worker exists while it holds or requests
leases. Pull also balances load naturally, because idle runners take the next item.

\textbf{Stage dependencies.} A stage becomes \texttt{QUEUED} only after its predecessor is published and that
publication is receipted (\S\ref{sec:mc}). Consumers read only the \emph{published} manifest, never a
prefix listing.

\textbf{Resources and fairness.} At acceptance, each job gets a resource profile from image count and decoded
image size (batch bytes alone do not predict peak memory) plus the model's VRAM. A lease matches only a
compatible pool, and GPU stages run only on tainted GPU pools. Ordering is \emph{weighted fair share across
tenants}, then oldest first. A per-tenant GPU concurrency cap (default 2) stops one partner's 50-job
burst from starving the others; unused share may be borrowed.

\textbf{Placement.} Work is placed by \emph{estimated finish time} (queue wait + measured stage runtime +
transfer). Prep runs in the home cloud. Stage 2 \emph{spills} only if
$\mathrm{ETA}_{remote} + t_{transfer} + 20\,\mathrm{min} < \mathrm{ETA}_{local}$ (hysteresis). It then copies and
verifies the \emph{prepared} output ($\approx$150--300\,MB, $\approx$\$0.02--0.04) rather than the raw 3\,GB
batch ($\approx$\$0.36). The report stage stays next to the identification output.

\section{VMs, Containers and Orchestration}
\textbf{Provisioning (IaC).} Terraform modules per cloud (VPC, VPN/BGP, EKS/GKE, node pools, buckets with
lifecycle rules, KMS, primary and standby databases, IAM) plus a global stack (DNS, witness). State is
encrypted, locked and access-restricted. GitHub Actions runs \texttt{plan} on pull requests and
\texttt{apply} after review, authenticating through OIDC federation, so CI holds no cloud keys. Helm charts
synced by Argo CD keep both clusters on identical, versioned manifests. Schema migrations and failover
drills are tested with each release.

\textbf{Holding the cap.} Node pools have \texttt{max\_size} system 1, CPU 7 and GPU 2 per cloud. The cap must
also hold during upgrades and repairs. Surge is therefore disabled (EKS \texttt{MINIMAL} node-group updates, GKE
zero-surge), so a node is removed before its replacement is created. Dedicated accounts and projects with
restricted provisioning roles stop anyone adding pools outside Terraform, and an alert fires at 19 VMs.
An \emph{unreachable} VM still counts: capacity is never reclaimed until its termination is confirmed.
CPU workers use spot instances, because a preemption is just another lease expiry. GPU workers and system
nodes are on-demand.

\textbf{Containers.} Each stage has one image: the supplied program plus the runner agent and its
libraries. Images are built once in CI, scanned, signed (cosign), pushed to both registries and deployed
\emph{by digest}. The GPU image pins CUDA and framework versions and a tested host-driver range. Model
weights are \emph{not} baked into the image (the same pattern as my A1 SmartPark deployment): an init
container fetches \texttt{model@version} from our bucket, verifies its SHA-256, and stores it in a
node-local, read-only, model-only cache. Tenant data never enters that cache.

\textbf{Isolation and scaling.} KEDA \emph{ScaledJobs} launch one single-use pod per eligible queued lease, and
count active and pending pods to avoid over-launching. A pod requests a lease only after its startup
checks pass, runs exactly one attempt and exits; an empty pull exits at once. Every tenant job therefore
gets a fresh pod with its own scratch \texttt{emptyDir}. Requests cover CPU, RAM, ephemeral disk and GPU,
which places one attempt per worker VM while leaving room for node agents. The cluster autoscaler works
within the pool bounds, and GPU pools scale to zero after 10\,min idle (one stays warm in business
hours). Pods run as non-root with a read-only root filesystem, all capabilities dropped and seccomp.
NetworkPolicy is default-deny: egress is allowed only to the coordinator, identity, DNS, model and storage
endpoints. This sharply reduces, but cannot eliminate, the risk of a third-party program exfiltrating
data.

\textbf{Provenance.} Each published stage run stores an immutable record: input and output manifest hashes,
attempt and epoch, image digest, program version, model name/version/SHA-256, framework/CUDA/driver
versions, GPU model, instance type, region, timings and exit code. The report embeds a provenance digest.
The same image and model can still differ slightly in floating point across GPU models, so the hardware
is recorded and pinned when bitwise reproducibility is required. Images and models referenced by retained
reports are kept for the report's lifetime.

\section{Health and Recovery}
\textbf{Readiness.} A startup check verifies the model checksum, GPU allocation and a CUDA self-test, free
scratch space, and that storage and the coordinator are reachable; only then does the runner claim work.
Node health comes from the kubelet and GPU (Xid) errors.

\textbf{Crashes.} A non-zero exit or OOM is reported by the agent. A lost pod, VM, preemption or partition
appears as missing heartbeats. The reaper locks the row, confirms expiry on the database clock, marks the
attempt \texttt{ABANDONED} and requeues the stage; the next claim increments the epoch.

\textbf{Stalls.} Heartbeats prove only that the agent is alive, not that useful work is happening, so they
also carry progress: output bytes, program progress where available, and GPU utilisation for stage 2
(an idle CPU does not mean a GPU kernel has stalled). No progress for 10\,min, or exceeding 2$\times$ the
historical p99 for the size class and hardware, kills and requeues the attempt. The agent also stops
itself when it cannot renew, but safety never depends on that (\S\ref{sec:fail}).

\textbf{Repeated failures} are classified:
(a)~\emph{transient program failures} are retried at most twice with exponential backoff and jitter, and an
OOM moves to a larger-memory pool;
(b)~\emph{deterministic input or configuration errors} are not retried and go to the partner with a reason;
(c)~\emph{infrastructure failures} have a separate budget (5 attempts or 24\,h) and lower the node's health
score, and 2 failures from different jobs within 1\,h quarantine the node.
An exhausted budget leaves the job \texttt{FAILED\_NEEDS\_REVIEW}: its data is kept, an alert fires, and the
queue continues. Cancellation invalidates leases and blocks publication.

\textbf{Logs and metrics.} Structured logs carry \texttt{tenant, job, stage, attempt, epoch, trace ID, image
digest, model hash} and failure category, never image contents or secrets. Metrics and alerts: oldest
queue age, stage latency by size and hardware, GPU utilisation and VRAM, lease-expiry and retry rates,
tenant fairness, object-copy failures, receipt-mirror backlog, replication lag, VM count vs.\ cap, egress
bytes and stalled finalisation.

\section{Failure Scenario: GPU VM Lost After Writing Its Output}\label{sec:fail}
\begin{table}[H]\centering\small
\begin{tabularx}{\linewidth}{@{}p{1.25cm}Y@{}}
\toprule
\textbf{Time} & \textbf{Event and state change} \\ \midrule
$t_0$ & G1 has claimed stage 2 of job J: \texttt{epoch=7}, attempt \texttt{A}. It writes \texttt{stage2/attempt-A/}
  with create-only writes, then a manifest of object versions and SHA-256. Only the coordinator can move
  the publication pointer. \\
$t_1$ & G1 becomes unreachable before committing; its heartbeats stop. Its storage credentials may outlive the
  lease (AWS STS sessions last $\geq$15\,min) but can write only \texttt{attempt-A/}, which nobody reads unless it is
  published. Credentials are therefore \emph{not} the safety mechanism. \\
$t_1$+90\,s & The reaper locks the row, confirms expiry on the DB clock, marks \texttt{A} \texttt{ABANDONED} and sets the
  stage \texttt{QUEUED}; \texttt{epoch} stays 7. A commit from G1 now fails, because the stage is not \texttt{RUNNING}. \\
$t_2$ & G2 claims the stage (\texttt{epoch=8}, attempt \texttt{B}), writes \texttt{attempt-B/} and commits:
  \texttt{UPDATE stage\_runs SET status='PUBLISHING', published\_attempt='B' WHERE job=J AND stage=2 AND attempt\_id='B'
  AND owner='G2' AND epoch=8 AND status='RUNNING' AND lease\_expires\_at > now()} $\rightarrow$ 1 row. Once the publication
  receipt is mirrored, a second transaction sets \texttt{SUCCEEDED} and queues stage 3. An identical repeated commit
  returns the same success. \\
$t_3$ & G1 returns and commits with \texttt{epoch=7}, attempt \texttt{A} $\rightarrow$ 0 rows $\rightarrow$ \texttt{409 STALE\_LEASE}.
  The agent discards its work and exits. Kubernetes has already deleted the pod, so the kubelet kills it on
  reconnect. \\
$t_3$+24\,h & GC confirms that \texttt{A} is unreferenced and deletes \texttt{attempt-A/}. \\
\bottomrule
\end{tabularx}
\end{table}
\vspace{-6pt}
\textbf{Why there is no duplicate or conflicting result.}
(a)~Attempts never share a path, and writes are create-only, so G1 cannot overwrite G2.
(b)~Exactly one attempt can satisfy the predicate.
(c)~Consumers follow the published pointer only, so an orphan is invisible.
(d)~\texttt{COMPLETED} and the outbox event are written in one transaction, and notifications carry a stable ID.
(e)~Lease time is the database's clock, so drift on G1 cannot help it.
The guarantee is one \emph{authoritative published result}, not one physical execution. \emph{Considered and
rejected:} adopting G1's verified orphan would save $\approx$6 GPU-min and is safe with create-only objects,
but it adds a second publication path, so we rerun instead.

\section{Multi-Cloud Operation}\label{sec:mc}
\textbf{Strategy: active-active compute, active-passive database writer (warm standby).} Both clouds run job
services and workers every day, so failover capacity is always warm and tested. The only singleton is
the PostgreSQL writer (AWS); GCP's job service writes to it over the VPN, and GCP holds an async replica.
A multi-master database would need $\geq$3 regions for quorum and a further third-party dependency,
which is too much for 100 jobs/day.

\textbf{Connectivity and egress.} AWS Site-to-Site VPN $\leftrightarrow$ GCP HA VPN (4 tunnels, BGP,
non-overlapping CIDRs), with TLS to the database and mTLS between services. Cross-cloud traffic consists
of DB replication, GCP-to-primary writes, receipt and report copies, and rare spills. A copier service
sends these through the VPN to private storage endpoints. Partners' presigned-URL traffic never crosses
clouds. Data-local placement cuts cross-cloud bytes from $\approx$9\,TB/month ($\approx$\$1{,}080) to
$\approx$30\,GB/month ($\approx$\$4), plus spills; a dedicated interconnect is not justified at this volume.

\textbf{Visibility rule (replication safety).} Three small immutable receipts (\emph{acceptance},
\emph{stage publication} and \emph{completion}) are mirrored to both clouds \emph{before} the matching state
becomes visible, i.e.\ before the \texttt{202}, before the next stage is queued, and before the partner is
notified. Each transition is two-step in the database (e.g.\ \texttt{PUBLISHING} $\rightarrow$ \texttt{SUCCEEDED}) with
the mirror in between, driven by an outbox worker, so a crash between the steps only delays them. Every fact anyone has seen therefore exists outside the primary, even when replication
lags. The cost is one cross-cloud object write ($<$1\,s) per stage.

\textbf{Dynamic failover (AWS unreachable).}
(1)~\emph{Detect and route:} DNS health checks from several locations and GCP probes fail for 3\,min, and
DNS sends all API traffic to GCP. Status (labelled ``last known'') and report downloads, which rely on
mirrored receipts, continue immediately.
(2)~\emph{Fence the old writer:} the AWS job services renew a 60\,s \emph{writer lease} (generation $g$)
in the witness. Every job service, in either cloud, opens a write transaction only while that lease has
$\geq$15\,s left, and statements time out after 5\,s, so after expiry plus a clock-skew margin nothing can still be writing to
the old primary. Each renewal also records the receipt-mirror backlog.
(3)~\emph{Promote only when safe:} if the lease has expired \emph{and} its last renewal reported backlog\,=\,0, GCP
promotes Cloud SQL as generation $g{+}1$ and reconciles from receipts. Missing accepted jobs are
re-created, and missing publications are restored with the \emph{same} attempt IDs, so no stage is ever
re-published differently. Unreceipted in-flight work was never visible and is simply rerun. Otherwise
(backlog $>$0, or the witness is down) the system stays read-only until an operator decides; fencing is
never bypassed.

\emph{Keeps operating:} new submissions (homed in GCP), GCP-homed jobs, status, and every report.
\emph{Paused, not lost:} AWS-homed jobs whose inputs are in S3.
Capacity drops to 10 VMs (20 GPU jobs/h), because the unreachable VMs still count against the cap.
Targets: read RTO $\approx$3\,min, write RTO $\approx$5\,min when the gate passes, RPO\,=\,0 for visible results.
\textbf{GCP outage:} AWS stays primary in degraded mode. It accepts and publishes with local receipts and a
non-zero backlog, which blocks automatic promotion until GCP returns and the backlog drains. GCP-homed jobs
pause. \textbf{Link-only partition} (both clouds healthy): AWS still renews the lease, so nothing is promoted;
GCP serves reads, and its runners finish current attempts but cannot publish until the link returns.
\textbf{Failback:} the old primary is rebuilt as a replica and switched over in a quiet window. Requests
carrying generation $g$ are refused.

\section{Cloud Security}
\textbf{Users.} Partners sign in through OIDC with MFA; the JWT's issuer, audience, signature and expiry are
validated, and the tenant is mapped server-side. Automation uses scoped OAuth client credentials.
\textbf{Services.} Workloads use workload identity (EKS Pod Identity, GKE Workload Identity), so no
static cloud keys exist. Internal APIs use mTLS, and database connections use TLS.

\textbf{Access control (defence in depth).}
(1)~The tenant comes from the token, never from the request body, and ownership is checked on every call.
(2)~PostgreSQL row-level security: \texttt{SET LOCAL app.tenant\_id} in each transaction, application roles
that are not table owners and lack \texttt{BYPASSRLS}, and a separate restricted role for the scheduler.
(3)~One bucket and one KMS key per tenant per cloud; both report copies and receipts are protected by the
same tenant checks.
(4)~Runners get only the exact input and model reads and attempt-prefix writes they need. Because STS
sessions last at least 15\,min, the coordinator's lease, not the credential, is the authority.
(5)~Presigned URLs are per object and short-lived.
Retiring a tenant's key crypto-shreds its data once retention and backup obligations are reconciled.

\textbf{Secrets.} Secrets live in AWS Secrets Manager / GCP Secret Manager, are read at run time through
workload identity and are rotated; databases use IAM authentication. CI runs secret scanning.
\textbf{Network isolation.} Workers and databases are private (no public IPs) and use private storage
endpoints. The API sits behind a WAF and rate limits, and admission control (Kyverno / Binary
Authorization) admits only signed images.
\textbf{Encryption.} TLS 1.2+ externally, mTLS internally, and IPsec between clouds. At rest: SSE-KMS/CMEK
with per-tenant keys, and KMS-encrypted databases, disks and backups. Audit trail: CloudTrail data events,
GCS data-access logs, and DB audit of every state transition.

\section{Trade-offs and Limitations}
\textbf{Safety over availability:} in an ambiguous partition the system may stay read-only rather than risk two
writers. \textbf{Receipts} add $<$1\,s per stage in exchange for RPO\,=\,0 on visible results. \textbf{Inputs are
not replicated}: this saves $\approx$\$1k/month but pauses home-cloud jobs during an outage.
\textbf{Scale-to-zero GPUs} save $\approx$\$2.7k/month for a $\approx$5\,min cold start. \textbf{Third-party
witness and DNS:} if either fails, failover falls back to an operator decision.
