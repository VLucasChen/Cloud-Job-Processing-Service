\textbf{Summary.} A two-provider design (AWS + GCP, Sydney) for partner-submitted image batches processed
by a CPU $\rightarrow$ GPU $\rightarrow$ CPU pipeline within a 20-VM / 4-GPU cap. Workers pull fenced leases from a
single transactional job store; outputs are create-only per attempt, and a conditional commit publishes
exactly one result per stage. Job metadata is replicated \emph{synchronously} between the clouds and
governed by a three-voter quorum (AWS, GCP, third-site witness), so failover is automatic, an isolated
old primary cannot acknowledge a write, and no acknowledged decision is lost. Bulk data stays in its home
cloud to avoid egress.

\section{Overview, Assumptions and Key Decisions}
Partners upload a 1--5\,GB image batch; each job runs \emph{prep} (CPU) $\rightarrow$
\emph{species ID} (GPU) $\rightarrow$ \emph{report} (CPU). Four principles drive the design.
(i)~One transactional store (PostgreSQL) holds job state, the queue and leases, so there is never a
dual-write between a queue and a database.
(ii)~\emph{Execution is at-least-once, publication is exactly-once}: workers pull fenced leases, write
create-only per-attempt objects, and a conditional update publishes exactly one attempt.
(iii)~\emph{Compute is active-active across AWS and GCP}, and jobs run data-locally to avoid egress.
(iv)~\emph{State is quorum-governed}: every commit is flushed synchronously in both clouds, and a
three-voter quorum (AWS, GCP, third-site witness) decides which database may accept writes. Two sites
alone cannot tell a dead peer from a broken link; a third voter can~\cite{gilbert-lynch,etcd-faq}.

\section{One Job's Lifecycle}
\begin{sloppypar}
\textbf{States.} Job: \texttt{UPLOADING} $\rightarrow$ \texttt{ACCEPTED} $\rightarrow$ \texttt{RUNNING}
$\rightarrow$ \texttt{COMPLETED}; side exits \texttt{FAILED\_NEEDS\_REVIEW}, \texttt{CANCELLED}. Each stage:
\texttt{QUEUED} $\rightarrow$ \texttt{RUNNING} $\rightarrow$ \texttt{SUCCEEDED}, with \texttt{RETRY\_WAIT} and
\texttt{FAILED}. Job and attempt IDs are UUIDs.
(1)~The partner signs in through its IdP; the job service validates the JWT (issuer, audience,
signature, expiry) and maps the partner to a tenant server-side.
(2)~\texttt{POST /jobs} (file list, sizes, SHA-256) picks the home cloud (healthy, earliest estimated
finish) and returns per-object multipart-upload URLs scoped to \texttt{jobs/\{id\}/input/} in the tenant
bucket (15\,min, renewable after re-authentication).
(3)~The client uploads directly; failed parts are retried individually, and abandoned uploads expire by
lifecycle rule.
(4)~\texttt{POST /jobs/\{id\}:submit} carries a tenant-scoped \texttt{Idempotency-Key} and request hash. The
service verifies sizes and SHA-256 (multipart ETags are not content hashes), then one transaction records
\texttt{ACCEPTED}, the immutable input manifest, pinned image and model versions and \texttt{PREP\_QUEUED}.
Because commits are synchronous, \texttt{202} means the acceptance is durable in \emph{both} clouds. A retry
returns the same job; reusing a key with a different request is rejected.
(5)~A ready CPU runner in the home cloud claims the prep lease.
(6)~It writes \texttt{stage1/attempt-\{uuid\}/}; the coordinator publishes it (\S\ref{sec:fail}), marking the
stage \texttt{SUCCEEDED} and queuing stage 2 in the same transaction. Stage 3 follows the same way.
(7)~The report is verified in the home cloud; one transaction records \texttt{COMPLETED}, the object
version and a notification outbox event, and a tracked copier adds the second copy in the other cloud.
Notifications are at-least-once with a stable event ID. \texttt{GET /jobs/\{id\}} shows stage, queue
position and ETA; reports download via 5-minute presigned URLs.
\end{sloppypar}

\section{Job Coordination and Placement}
\textbf{Acceptance and tracking.} The \texttt{jobs} and \texttt{stage\_runs} tables are the single source of
truth. Each stage row holds \texttt{status}, \texttt{epoch}, \texttt{attempt\_id}, \texttt{owner},
\texttt{lease\_expires\_at} (database clock) and \texttt{published\_attempt}. Load is $<$1\,write/s, so a
separate broker (SQS/Pub/Sub) would only add a dual-write hazard.

\textbf{Worker discovery and assignment (pull).} A small \emph{runner agent} in each stage image
authenticates with workload identity and calls \texttt{POST /leases} with its capabilities (cloud, pool,
allocatable memory, GPU model and VRAM, readiness), checked against the pool's configured identity. The
coordinator selects an eligible row with \texttt{SELECT \ldots FOR UPDATE SKIP LOCKED}~\cite{pg-select} and, in
the same transaction, sets \texttt{RUNNING}, increments \texttt{epoch}, creates a new \texttt{attempt\_id},
records the owner and grants a 90\,s lease, renewed every 30\,s. Only a claim increments the epoch. No
registry is needed: a worker exists while it holds or requests leases, and idle (faster) runners ask
sooner, which balances load naturally.

\textbf{Dependencies, resources and fairness.} A stage becomes \texttt{QUEUED} only in the transaction that
marks its predecessor \texttt{SUCCEEDED}; consumers require \texttt{SUCCEEDED} and read only the published
manifest. Each job gets a resource profile from image count and decoded size (batch bytes alone do not
predict peak memory) plus model VRAM; a lease matches only a compatible pool, and GPU stages run only on
tainted GPU pools. Ordering is weighted fair share across tenants, then oldest first, with a per-tenant
GPU cap (default 2) whose unused share may be borrowed.

\textbf{Placement.} Work is placed by estimated finish time (queue wait + measured runtime + transfer).
Prep runs in the home cloud. Stage 2 \emph{spills} only if
$\mathrm{ETA}_{remote} + t_{transfer} + 20\,\mathrm{min} < \mathrm{ETA}_{local}$, copying the verified
\emph{prepared} output ($\approx$150--300\,MB) instead of the raw 3\,GB batch: 10--20$\times$ less egress. The
report stage stays next to the identification output.

\section{VMs, Containers and Orchestration}
\textbf{Provisioning (IaC).} Terraform modules per cloud (VPC, VPN/BGP, EKS/GKE, node pools, buckets with
lifecycle rules, KMS, IAM) plus a global stack (DNS, witness). State is encrypted and locked. GitHub
Actions runs \texttt{plan} on pull requests and \texttt{apply} after review, using OIDC federation, so CI
holds no cloud keys. Kubernetes manifests are \emph{plain YAML} (shared base plus small per-cloud files),
extending my A1 SmartPark \texttt{kubectl} workflow~\cite{smartpark}: CI substitutes signed image digests and
runs \texttt{kubectl apply} on both clusters, and a scheduled \texttt{kubectl diff} reports drift.
PostgreSQL + Patroni runs as a StatefulSet pinned to each cloud's system/state node, on an encrypted SSD
volume with the Linux watchdog enabled~\cite{patroni-watchdog}. Failover drills run with each release.

\textbf{Holding the cap.} Node pools have \texttt{max\_size} system 1, CPU 7 and GPU 2 per cloud. Upgrades
and repairs must not exceed it, so a node is removed before its replacement is created (EKS
\texttt{MINIMAL} update strategy, GKE \texttt{maxSurge=0}, \texttt{maxUnavailable=1})~\cite{eks-update,gke-upgrade}. Restricted provisioning roles stop pools
being added outside Terraform; an alert fires at 19 VMs. An \emph{unreachable} VM still counts until its
termination is confirmed. CPU workers use spot (a preemption is just a lease expiry); GPU and system/state
nodes are on-demand.

\textbf{Containers.} One image per stage: the supplied program, the runner agent and pinned libraries, built
once, scanned, signed with cosign~\cite{cosign}, pushed to both registries and deployed \emph{by digest}. The
GPU image pins CUDA, framework and a tested driver range. As in A1, model weights are not baked into the
image: an init container fetches \texttt{model@version}, verifies its SHA-256 and keeps it in a node-local,
read-only, model-only cache; tenant data never enters it.

\textbf{Isolation and scaling.} Each attempt is a finite Kubernetes Job: KEDA \emph{ScaledJobs}~\cite{keda}
launch one single-use pod per eligible queued lease; the \texttt{accurate} strategy subtracts pending Jobs to avoid over-launch. A pod
claims a lease only after its startup checks pass, runs one attempt and exits, so every tenant job gets
a fresh pod and scratch \texttt{emptyDir}. Requests cover CPU, RAM, ephemeral disk and GPU, and required
anti-affinity places one attempt per worker VM. The cluster autoscaler works within pool bounds; GPU pools
scale to zero after 10\,min idle (one warm in business hours). Pods run non-root with a read-only root
filesystem, no capabilities and seccomp. Default-deny NetworkPolicy allows egress only to the
coordinator, identity, DNS, model and storage endpoints, sharply limiting exfiltration by third-party code.

\section{Health and Recovery}
\textbf{Readiness.} A startup check verifies the model checksum, GPU allocation and a CUDA self-test,
scratch space, and storage and coordinator reachability before any claim. Node health comes from the
kubelet and GPU (Xid) errors; DB health from Patroni's REST checks and etcd quorum status.
\textbf{Crashes.} A non-zero exit or OOM is reported by the agent; a lost pod, VM, preemption or partition
appears as missing heartbeats. The reaper locks the row, confirms expiry on the database clock, marks the
attempt \texttt{ABANDONED} and requeues; the next claim increments the epoch.
\textbf{Stalls.} Heartbeats carry progress (output bytes, program progress, GPU utilisation for stage 2;
an idle CPU does not mean a stalled GPU kernel). No progress for 10\,min, or exceeding 2$\times$ the p99
for the size class and hardware, kills and requeues the attempt. The agent stops itself when it cannot
renew, but safety never depends on that (\S\ref{sec:fail}).

\textbf{Repeated failures} are classified: (a)~transient program failures get at most two retries with
exponential backoff and jitter, and an OOM moves to a larger pool; (b)~deterministic input or
configuration errors are not retried and are returned to the partner with a reason; (c)~infrastructure
failures have a separate budget (5 attempts or 24\,h) and lower the node's health score, and 2 failures
from different jobs within 1\,h quarantine the node. Budgets are initial defaults, tuned by fault injection.
An exhausted budget leaves the job \texttt{FAILED\_NEEDS\_REVIEW} with data kept and an alert raised.

\textbf{Logs and metrics.} Structured logs carry \texttt{tenant, job, stage, attempt, epoch, trace ID, image
digest, model hash} and failure category, never images or secrets. Alerts: oldest queue age, stage p50/p99
by hardware, GPU utilisation/VRAM, lease-expiry and retry rates, tenant fairness, sync-standby state,
etcd quorum, report-copy backlog, VM count vs.\ cap and egress bytes.

\section{Failure Scenario: GPU VM Lost After Writing Its Output}\label{sec:fail}
Only the coordinator publishes, and only through a fenced conditional commit; Table~\ref{tab:fail} traces
the required scenario step by step.
\begin{table}[tb]\centering\small
\begin{tabularx}{\linewidth}{@{}L{1.25cm}Y@{}}
\toprule
\textbf{Time} & \textbf{Event and state change} \\ \midrule
$t_0$ & G1 has claimed stage 2 of job J: \texttt{epoch=7}, attempt \texttt{A}. It writes \texttt{stage2/attempt-A/}
  with create-only writes, then a manifest of object versions and SHA-256. Only the coordinator can move
  the publication pointer. \\
$t_1$ & G1 becomes unreachable before committing; heartbeats stop. Its storage credentials may outlive the lease
  (AWS STS sessions last $\geq$15\,min~\cite{aws-sts}) but can write only \texttt{attempt-A/}, which nobody reads unless
  published, so credentials are \emph{not} the safety mechanism. \\
$t_1$+90\,s & The reaper locks the row, confirms expiry, marks \texttt{A} \texttt{ABANDONED} and sets \texttt{QUEUED}; \texttt{epoch}
  stays 7. A commit from G1 now fails, because the stage is not \texttt{RUNNING}. \\
$t_2$ & G2 claims (\texttt{epoch=8}, attempt \texttt{B}), writes \texttt{attempt-B/} and commits in one short transaction: lock
  the row, then \texttt{UPDATE stage\_runs SET status='SUCCEEDED', published\_attempt='B' WHERE job=J AND stage=2 AND
  attempt\_id='B' AND owner='G2' AND epoch=8 AND status='RUNNING' AND lease\_expires\_at > clock\_timestamp()}
  $\rightarrow$ 1 row, and queue stage 3. \texttt{clock\_timestamp()} is used because \texttt{now()} is fixed at
  transaction start~\cite{pg-time}. A repeated identical commit returns the recorded success. \\
$t_3$ & G1 returns and commits with \texttt{epoch=7}, attempt \texttt{A} $\rightarrow$ 0 rows $\rightarrow$ \texttt{409 STALE\_LEASE}.
  The agent discards its work; Kubernetes has already deleted the pod, so the kubelet kills it on reconnect. \\
$t_3$+24\,h & GC confirms that \texttt{A} is unreferenced and deletes \texttt{attempt-A/}. \\
\bottomrule
\end{tabularx}
\caption{Recovery timeline for the required failure scenario.}\label{tab:fail}
\end{table}
\textbf{Why there is no duplicate or conflicting result.} (a)~Attempts never share a path and writes are
create-only, so G1 cannot overwrite G2. (b)~Exactly one attempt can satisfy the predicate (a fencing token
checked by the store itself~\cite{kleppmann-lock,ddia}), and cancellation takes the same row lock. (c)~Consumers
require \texttt{SUCCEEDED} plus the pointer, so an orphan is invisible. (d)~\texttt{COMPLETED} and the outbox
event share one transaction; notifications carry a stable ID. (e)~Leases use the database clock, and
because leases live in the synchronously replicated store, the same rules hold after a DB failover. The
guarantee is one \emph{authoritative published result}, not one physical execution. \emph{Considered and
rejected:} adopting G1's verified orphan saves $\approx$6 GPU-min but adds a second publication path.

\section{Multi-Cloud Operation}\label{sec:mc}
\textbf{Strategy: active-active compute, quorum-governed state.} Both clouds run job services and workers
every day. PostgreSQL runs one Patroni-managed node per cloud: the \emph{leader} (normally AWS) and a
\emph{synchronous standby} (GCP) with \texttt{synchronous\_commit=on}, so a commit is acknowledged only after
it is flushed in both clouds~\cite{pg-syncrep}. Patroni keeps its leader key in a three-voter etcd cluster
(AWS, GCP, witness)~\cite{patroni-sync}. Job services in both clouds write to the current leader through a
Patroni-aware endpoint.

\textbf{Connectivity and egress.} AWS Site-to-Site VPN $\leftrightarrow$ GCP HA VPN (4 tunnels, BGP,
non-overlapping CIDRs)~\cite{gcp-havpn}, with mTLS for services, etcd peers and replication. Cross-cloud traffic
is DB replication, writes from the GCP job service, report copies and rare spills; partners'
presigned-URL traffic never crosses clouds. Replicating every raw input would move $\approx$9\,TB/month
($\approx$\$1.0--1.5k); data-local placement leaves reports (100$\times$10\,MB$\times$30 $\approx$
30\,GB/month) plus small DB/WAL traffic and occasional spills ($\approx$\$0.02--0.05 each).

\textbf{Why failover is safe and automatic.} (1)~\emph{An isolated old leader cannot acknowledge anything}: its
commits wait for the unreachable standby, and switching to asynchronous mode requires updating the
\texttt{/sync} key in etcd, which needs a quorum it no longer has. Once its leader key expires (TTL 30\,s) it
demotes itself; the watchdog resets the node if Patroni itself hangs. (2)~\emph{Only an up-to-date node can be
promoted}: Patroni never auto-promotes a member that is not in \texttt{/sync}, and a member stays a
synchronous standby in PostgreSQL for as long as \texttt{/sync} lists it, so it leaves the list (a quorum
write) \emph{before} the leader stops waiting for it~\cite{patroni-sync}. (3)~\emph{Degraded mode is explicit}: the surviving
leader keeps writing asynchronously only after recording in etcd that the other node is ineligible; that
node must catch up (via \texttt{pg\_rewind}) before it can rejoin the list. (4)~\emph{No cancelled commit
waits}: a cancelled wait leaves a commit visible locally but unreplicated~\cite{patroni-sync}, so clients
never cancel \texttt{COMMIT}; an unknown outcome is retried idempotently. Hence no acknowledged decision is
lost or forked, and no human is needed.

\section{Cloud Security}
\textbf{Users.} Partners sign in through OIDC with MFA; issuer, audience, signature and expiry are validated
and the tenant is mapped server-side. Automation uses scoped OAuth client credentials.
\textbf{Services.} Workload identity (EKS Pod Identity, GKE Workload Identity)~\cite{eks-pod-identity,gke-wi}
means no static cloud keys. Internal APIs, PostgreSQL, Patroni REST and etcd use mTLS with
per-service certificates.
\textbf{Access control (defence in depth).} (1)~The tenant comes from the token, never the request body;
ownership is checked on every call. (2)~Row-level security~\cite{pg-rls} via \texttt{SET LOCAL app.tenant\_id}
per transaction, with application roles that are not table owners and lack \texttt{BYPASSRLS}, and a separate
restricted coordinator role. (3)~One bucket and one KMS key per tenant per cloud. (4)~Runners get only the
exact input/model reads and attempt-prefix writes they need, and cannot publish or delete reports; since STS
sessions last $\geq$15\,min, the lease, not the credential, is the authority. (5)~Presigned URLs are per
object and short-lived. Retiring a tenant key crypto-shreds its data once retention duties are met.
\textbf{Secrets} live in AWS Secrets Manager / GCP Secret Manager, are read at run time and rotated; CI runs
secret scanning. \textbf{Network isolation:} workers and databases have no public IPs and use private
endpoints; the API sits behind a WAF and rate limits; admission control admits only signed images.
\textbf{Encryption:} TLS 1.2+ externally, mTLS internally, IPsec between clouds; SSE-KMS/CMEK per tenant
and encrypted volumes and backups at rest. Audit: CloudTrail data events, GCS access logs, DB audit of
every state transition.
